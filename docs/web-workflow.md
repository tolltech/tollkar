# Запуск, публикация и сквозная проверка веб-караоке

## Локальный запуск

Нужны .NET SDK из `global.json`, Node.js 22.18+ (для Vite — не ниже 22.12)
и npm. Команды выполняются из корня репозитория. Медиаплеер использует HTML5,
поэтому LibVLC для веб-приложения не требуется.

```sh
dotnet restore src/Tollkar.Web/Tollkar.Web.csproj
dotnet tool restore
dotnet ef database update --project src/Tollkar.Web --startup-project src/Tollkar.Web --context WebDbContext
dotnet run --project src/Tollkar.Web/Tollkar.Web.csproj --launch-profile http
```

Откройте `http://localhost:5074` (переход на Vite `http://localhost:5173`).
Зарегистрируйтесь и поместите поддерживаемые браузером MP4 в `src/Tollkar.Web/songs`.
Имена `Исполнитель - Название.mp4` определяют метаданные. После сканирования
найдите песни на `/queue`, добавьте их и нажмите «Играть сейчас». На `/player`
включите звук пользовательским жестом. Разрешение звука действует только в этой вкладке.

## Публикация на macOS за Caddy

Перед обновлением сделайте резервную копию каталога публикации, включая обе
SQLite-базы и их `-wal`/`-shm`, если они есть. Скрипт управляет сервером через
LaunchAgent, но не делает резервную копию и не откатывает изменения автоматически.
Запускайте его от того же пользователя, которому принадлежит LaunchAgent.

```sh
./publish.sh /Users/server/tollkar
```

Аргумент — папка вне репозитория (можно с пробелами, относительные пути допустимы).
Нужны .NET SDK из `global.json`, Node.js/npm, `rsync`, `curl` и macOS `launchctl`.
В `~/Library/LaunchAgents/local.tollkar.web.plist` должен существовать агент с label
`local.tollkar.web`, `WorkingDirectory`, равным аргументу скрипта, и сервером на
`http://127.0.0.1:5080`. Агент может быть загружен или выгружен: после сборки скрипт
останавливает его, только если он загружен, и в обоих случаях запускает лишь после
успешной миграции. Несовпадение plist проверяется до сборки и изменения публикации.
Скрипт собирает Release во временной папке; `dotnet publish` выполняет `npm ci`,
проверку TypeScript и сборку SPA.
При ошибке сборки существующая публикация не изменяется. Результат предназначен для
текущей ОС/архитектуры машины сборки; для macOS выполняйте скрипт на целевом Mac.
На сервере нужен ASP.NET Core Runtime 10, Node.js для запуска не требуется.

После успешной сборки скрипт останавливает загруженный LaunchAgent и копирует приложение без
удаления существующих файлов. Он исключает
`*.db*`, `*.sqlite*`, `songs/`, `logs/`, `Logs/`, `*.log*`, `data/`, `keys/`, `backups/`.
Существующие `appsettings*.json` сохраняются; отсутствующие копируются из сборки.
Новые настройки следующих релизов нужно самостоятельно перенести в серверный конфиг.
Устаревшие файлы релизов не удаляются: это сознательный выбор в пользу сохранности
данных. Не храните данные под именами файлов приложения или внутри `wwwroot`.

В конце в режиме Production выполняется `dotnet Tollkar.Web.dll --migrate-databases`:
отсутствующая Identity-база создаётся EF-миграциями, существующая обновляется;
каталог создаётся или обновляется существующим версионированным SQL-инициализатором.
HTTP-сервер и сканер песен в этом режиме не запускаются. Ошибка миграции завершает
скрипт с ненулевым кодом; файлы приложения уже обновлены, а одна из баз могла быть
успешно обновлена. LaunchAgent остаётся выгруженным: не запускайте сервис до устранения
ошибки; для отката восстановите резервную копию вместе со старым релизом. Две базы
не образуют общую транзакцию.
После успешной миграции скрипт загружает LaunchAgent, перезапускает процесс и до
30 секунд ожидает ответ `/api/health` на порту 5080. Ошибка запуска или health check
завершает публикацию с ненулевым кодом и командой для диагностики сервиса.

### Копирование без перезапуска и миграций

Для обновления только файлов приложения используйте:

```sh
./publish-files.sh /Users/server/tollkar
```

Для локальной серверной папки `/Volumes/tollmini/_server/tollkar` доступна короткая
команда `./publish-files-server.sh`. Скрипт выполняет ту же Release-сборку и копирует
backend/frontend с той же защитой баз, песен, логов, ключей и существующих конфигов,
но не читает и не изменяет LaunchAgent, не запускает миграции и не проверяет health.
Запущенный процесс продолжает использовать уже загруженные сборки до ручного
перезапуска; статические frontend-файлы могут обновиться раньше backend-процесса.
Этот режим не предназначен для релиза, которому нужны миграции базы данных.

По умолчанию в папке публикации находятся `tollkar-web.db`, `tollkar-library.db`,
`songs/` и `logs/`. Миграции читают конфигурацию **целевой папки** и переменные
`ConnectionStrings__WebDatabase`, `Library__DatabasePath`, `Library__SongsPath`.
Если переопределяете пути, используйте одинаковые настройки при публикации и запуске,
заранее создайте родительские папки баз и включите внешние данные в резервное копирование.
Не передавайте переменные, указывающие на посторонние базы. Базы должны быть разными.

LaunchAgent должен запускать приложение из папки публикации с эквивалентными параметрами:

```sh
cd /Users/server/tollkar
ASPNETCORE_ENVIRONMENT=Production DOTNET_ENVIRONMENT=Production \
  dotnet Tollkar.Web.dll --urls http://127.0.0.1:5080
```

Vostok.Logging пишет события приложения, ASP.NET Core, Identity и EF Core в файлы
с базовым путём `logs/web.log`. Файлы дописываются при перезапуске и ротируются при
достижении 100 МБ; сохраняются пять последних частей, к которым Vostok добавляет
числовые суффиксы, например `web-1.log`. Базовый путь можно переопределить настройкой
`VostokLogging:FilePath` или переменной `VostokLogging__FilePath`; относительный
путь разрешается от content root приложения. Штатные события в консоль не дублируются.
Ошибки до инициализации логгера и внутренние ошибки файлового приёмника могут
остаться в stderr, поэтому сервисный менеджер должен сохранять его диагностику.

Для постоянной работы используйте указанный выше LaunchAgent с `RunAtLoad` и
`KeepAlive`, рабочей папкой публикации и переменными окружения Production.
Сохраняйте защищённое хранилище ASP.NET Core Data Protection keys сервисного
пользователя: его смена или удаление ключей сделают существующие cookies недействительными.

Пример Caddyfile (замените домен своим, настройте DNS и доступность портов 80/443):

```caddyfile
karaoke.example.com {
    reverse_proxy 127.0.0.1:5080
}
```

Caddy обслуживает HTTPS и проксирует HTTP/WebSocket в Kestrel. Приложение принимает
`X-Forwarded-For` и `X-Forwarded-Proto` только от стандартных доверенных loopback-proxy;
обработка заголовков выполняется до HTTPS-редиректа и аутентификации.
Не открывайте порт Kestrel наружу и не включайте доверие ко всем proxy.
Не добавляйте Caddy `file_server` для папки публикации: базы, конфиги и песни приватны,
видео выдаётся только через авторизованный API. Production cookies требуют HTTPS.

Запускайте ровно один серверный процесс. Очереди сохраняются в SQLite, но текущая
песня и таймлайн сбрасываются при рестарте. После запуска проверьте `/api/health`,
вход, создание пользователя через `/admin`, прямое открытие `/queue`, `/player` и `/admin`,
SignalR и media с Range (206). Публичная регистрация закрыта; начальная учётная запись `admin`
должна быть создана отдельно до развёртывания этой версии.
Не публикуйте Vite dev server.

## Приёмочные сценарии

Используйте две короткие заведомо воспроизводимые песни A и B. Для ошибок —
отдельный тестовый MP4. Проверки удаления проводите только на тестовых файлах.

| Сценарий | Действия | Ожидаемый результат |
| --- | --- | --- |
| Две вкладки одного пользователя | Откройте `/queue` и `/player` в одном профиле; добавьте A/B, выберите A, измените порядок, паузу и позицию | Обе вкладки показывают одну очередь и выбор; два плеера получают одинаковый таймлайн |
| Два пользователя | В отдельном профиле браузера войдите как B; изменяйте очередь/воспроизведение A | Каталог общий, очередь и проигрывание B не меняются; вкладки одного профиля разделяют cookie и не подходят для разных пользователей |
| Потеря SignalR | Разорвите WebSocket в тестовом proxy или временно отключите сеть вкладки, оставив сервер работающим; измените очередь со второго устройства | После обнаружения разрыва плеер приостанавливается, управление блокируется; после восстановления свежий snapshot возвращает очередь и позицию, пропущенные команды не повторяются |
| Перезапуск сервера | Остановите и снова запустите тестовый сервер | Клиент переподключается и принимает новый счётчик версий; очередь остаётся, выбор очищен |
| Завершение песни | Откройте два плеера одного пользователя, дождитесь конца A, затем B | На A происходит ровно один переход к B; после B выбор очищен, обе записи остаются в очереди |
| Очистка очереди | Выберите A, добавьте B, нажмите «Очистить очередь», затем дождитесь конца A | B удаляется сразу; A продолжает играть и удаляется при завершении, после чего очередь и выбор пусты |
| Нет файла | Удалите тестовый файл после индексации и попробуйте воспроизвести до следующего сканирования | Media возвращает 404, UI показывает ошибку; «Следующая» доступна; после сканирования удалённая песня исчезает из очереди |
| Ошибка медиа | Выберите повреждённый MP4 или неподдерживаемый кодек, в том числе с читаемыми метаданными | UI показывает ошибку, таймер не пропускает песню автоматически; перейти дальше можно вручную |

Отключение сети браузера не всегда немедленно закрывает существующий WebSocket:
дождитесь индикации восстановления. Серверный таймлайн продолжает идти во время
разрыва. Если все плееры закрыты, переход по завершению ждёт возвращения плеера.

## Автоматические проверки и их границы

`./handoff.sh` запускает lint, Node-тесты, production-сборку клиента, сборку решения
и все .NET-тесты. `RealtimeTests` проверяет два соединения одного пользователя,
изоляцию пользователей, восстановление пропущенных событий, гонку завершений и
исчерпание очереди через HTTP и SignalR WebSockets на TestServer.
`MediaTests` проверяет доступ, диапазоны и отсутствующие файлы; клиентские тесты —
версии snapshot, интерполяцию и запрет автоперехода при ошибке медиа.
Это не автоматизация настоящего браузера: кодеки, autoplay, звук, полноэкранный
режим и сетевые ограничения конкретного браузера проверяются по таблице вручную.
