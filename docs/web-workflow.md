# Запуск, публикация и сквозная проверка веб-караоке

## Локальный запуск

Нужны .NET SDK из `global.json`, Node.js 22.18+ (для Vite — не ниже 22.12)
и npm. Команды выполняются из корня репозитория. Медиаплеер использует HTML5,
поэтому LibVLC для веб-приложения не требуется.

```sh
dotnet restore src/Tollkar.Web/Tollkar.Web.csproj
dotnet tool restore
dotnet ef database update --project src/Tollkar.Web --startup-project src/Tollkar.Web --context WebDbContext
dotnet run --project src/Tollkar.Web/Tollkar.Web.csproj --launch-profile http
```

Откройте `http://localhost:5074` (переход на Vite `http://localhost:5173`).
Зарегистрируйтесь и поместите поддерживаемые браузером MP4 в `src/Tollkar.Web/songs`.
Имена `Исполнитель - Название.mp4` определяют метаданные. После сканирования
найдите песни на `/queue`, добавьте их и нажмите «Играть сейчас». На `/player`
включите звук пользовательским жестом. Разрешение звука действует только в этой вкладке.

## Публикация

```sh
dotnet publish src/Tollkar.Web/Tollkar.Web.csproj -c Release -o _tmp/publish/web
```

Публикация сама выполняет `npm ci`, проверку TypeScript и production-сборку SPA.
В результате должны присутствовать `Tollkar.Web.dll` и `wwwroot/index.html` с assets.
На сервере нужен ASP.NET Core Runtime 10; Node.js нужен на машине сборки, но не
для запуска опубликованного приложения. Переносите весь каталог публикации.

До первого запуска задайте абсолютные постоянные пути (пример для POSIX shell):

```sh
export ConnectionStrings__WebDatabase='Data Source=/srv/tollkar/data/identity.db'
export Library__DatabasePath='/srv/tollkar/data/library.db'
export Library__SongsPath='/srv/tollkar/songs'
export ASPNETCORE_ENVIRONMENT=Production
```

Каталоги нужно заранее создать и предоставить сервисному пользователю права на
запись. Базы Identity и каталога должны быть разными. Песни не входят в публикацию.
Не размещайте базы и песни внутри `wwwroot`. Сохраняйте их отдельно от релизов.

Сделайте резервные копии обеих баз при остановленном приложении. Из исходников
того же релиза с теми же переменными окружения примените миграции Identity:

```sh
dotnet tool restore
dotnet ef database update --project src/Tollkar.Web --startup-project src/Tollkar.Web --context WebDbContext
```

Схема каталога обновляется при запуске. Для отката схемы восстановите резервную
копию вместе с предыдущим релизом; данные после резервного копирования потеряются.
Миграции на production выполняет оператор, не HTTP-запрос и не старт приложения.

Запускайте из каталога опубликованного приложения: `dotnet Tollkar.Web.dll`.
Настройте HTTPS endpoint Kestrel и сертификат через конфигурацию развёртывания;
пароли сертификатов передавайте через защищённое хранилище, не через Git.
Production cookies требуют HTTPS. Если TLS завершается на reverse proxy,
нужны отдельно настроенные доверенные forwarded headers и поддержка WebSocket
для `/api/karaoke`; текущий код не настраивает доверие к proxy автоматически.
Не включайте доверие ко всем отправителям forwarded headers.

Запускайте ровно один серверный процесс. Закрепите сервисного пользователя и
постоянное защищённое хранилище его ASP.NET Core Data Protection keys: иначе
после смены контейнера/пользователя существующие cookies могут стать недействительными.
Очереди сохраняются в SQLite, но текущая песня и таймлайн сбрасываются при рестарте.

После запуска проверьте `/api/health`, регистрацию/вход, прямое открытие `/queue`
и `/player`, соединение SignalR и запрос media с Range (206). Не публикуйте Vite dev server.

## Приёмочные сценарии

Используйте две короткие заведомо воспроизводимые песни A и B. Для ошибок —
отдельный тестовый MP4. Проверки удаления проводите только на тестовых файлах.

| Сценарий | Действия | Ожидаемый результат |
| --- | --- | --- |
| Две вкладки одного пользователя | Откройте `/queue` и `/player` в одном профиле; добавьте A/B, выберите A, измените порядок, паузу и позицию | Обе вкладки показывают одну очередь и выбор; два плеера получают одинаковый таймлайн |
| Два пользователя | В отдельном профиле браузера войдите как B; изменяйте очередь/воспроизведение A | Каталог общий, очередь и проигрывание B не меняются; вкладки одного профиля разделяют cookie и не подходят для разных пользователей |
| Потеря SignalR | Разорвите WebSocket в тестовом proxy или временно отключите сеть вкладки, оставив сервер работающим; измените очередь со второго устройства | После обнаружения разрыва плеер приостанавливается, управление блокируется; после восстановления свежий snapshot возвращает очередь и позицию, пропущенные команды не повторяются |
| Перезапуск сервера | Остановите и снова запустите тестовый сервер | Клиент переподключается и принимает новый счётчик версий; очередь остаётся, выбор очищен |
| Завершение песни | Откройте два плеера одного пользователя, дождитесь конца A, затем B | На A происходит ровно один переход к B; после B выбор очищен, обе записи остаются в очереди |
| Нет файла | Удалите тестовый файл после индексации и попробуйте воспроизвести до следующего сканирования | Media возвращает 404, UI показывает ошибку; «Следующая» доступна; после сканирования удалённая песня исчезает из очереди |
| Ошибка медиа | Выберите повреждённый MP4 или неподдерживаемый кодек, в том числе с читаемыми метаданными | UI показывает ошибку, таймер не пропускает песню автоматически; перейти дальше можно вручную |

Отключение сети браузера не всегда немедленно закрывает существующий WebSocket:
дождитесь индикации восстановления. Серверный таймлайн продолжает идти во время
разрыва. Если все плееры закрыты, переход по завершению ждёт возвращения плеера.

## Автоматические проверки и их границы

`./handoff.sh` запускает lint, Node-тесты, production-сборку клиента, сборку решения
и все .NET-тесты. `RealtimeTests` проверяет два соединения одного пользователя,
изоляцию пользователей, восстановление пропущенных событий, гонку завершений и
исчерпание очереди через HTTP и SignalR WebSockets на TestServer.
`MediaTests` проверяет доступ, диапазоны и отсутствующие файлы; клиентские тесты —
версии snapshot, интерполяцию и запрет автоперехода при ошибке медиа.
Это не автоматизация настоящего браузера: кодеки, autoplay, звук, полноэкранный
режим и сетевые ограничения конкретного браузера проверяются по таблице вручную.
